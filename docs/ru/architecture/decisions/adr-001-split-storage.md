# ADR-001: Разделение структурированного и векторного хранилищ

## Статус
Принято

## Контекст
Система работает с двумя разными категориями данных:
- **Структурированные** — метаданные аудио, исходные транскрипты, записи о спикерах, временные метки.
- **Векторные** — эмбеддинги чанков (обычно 768+ измерений), эмбеддинги саммари различной длины.

Поисковые запросы должны сочетать фильтрацию по структурированным атрибутам (например, диапазон дат, идентификаторы спикеров) с векторным сравнением по схожести. Главный вопрос — хранить ли все данные в одной СУБД или разделить их.

Дополнительный вопрос — где выполнять этап структурированной фильтрации при поиске: внутри самой векторной базы данных или с предварительной фильтрацией в реляционном хранилище (см. также [ADR-003](adr-003-postgresql-prefiltering.md)).

## Решение
Использовать **две раздельные системы хранения**:
- **PostgreSQL** — исключительно для структурированных данных (транскрипты, метаданные, записи о спикерах).
- **Qdrant** — для всех векторных данных и для **фильтрации на основе полезной нагрузки (payload)**.

Во время поиска система **никогда не обращается к PostgreSQL**. Как векторный поиск по схожести, так и структурированная фильтрация выполняются внутри Qdrant одним gRPC-вызовом (см. [ADR-004](adr-004-hybrid-search.md)). Альтернативный подход с предварительной фильтрацией в PostgreSQL ([ADR-003](adr-003-postgresql-prefiltering.md)) был отклонён из-за неприемлемой задержки, вызванной дополнительными циклами обмена данными и усложнением логики на стороне приложения.

## Последствия
- **Положительные**:
  - У структурированных и векторных рабочих нагрузок принципиально разные паттерны доступа и требования к масштабированию; разделение устраняет взаимный конфликт доступа.
  - Поисковый путь замыкается внутри Qdrant — без дополнительных сетевых обращений для фильтрации, что обеспечивает предсказуемую и низкую задержку.
  - Эта архитектура оказалась чище, чем отклонённый двухэтапный подход ([ADR-003](adr-003-postgresql-prefiltering.md)), при котором постгрес-фильтрация добавляла циклы обмена, не давая значительного прироста производительности в нашем масштабе.
- **Отрицательные**:
  - Эксплуатация двух систем баз данных повышает инфраструктурную сложность (мониторинг, резервное копирование, распределение ресурсов).
  - В некоторых последующих сценариях (например, получение полных транскриптов после поиска) всё равно требуется дополнительное обращение к PostgreSQL; однако это шаг чтения после ранжирования, который не влияет на поисковый опыт.
